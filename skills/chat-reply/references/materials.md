# 聊天材料准备

材料层负责取得并整理当前任务的上下文，完成后交给回复阶段生成有活人感的表达。

## 1. 确定已有材料与缺口

先识别待回复消息、用户这一轮的目标，以及用户提供的聊天和补充说明。结合当前话题、双方已知背景、对话语气和用户明确表达的想法整理上下文；这些信息是理解和表达的依据，不是必须逐项回应的清单。只整理与本轮回复有关的内容；足以完成回复时直接进入第 3 步。

用户明确要求读取微信历史时执行查询。否则，仅在会话已明确且关键上下文不足时补查；会话无法确定或缺口属于用户尚未表达的当前意愿时，向用户澄清。用户提供微信 ID 时，直接用该 ID 查询，不先猜联系人名称。

## 2. 按需取得微信上下文

1. 调用 `list_wechat_sessions`，用用户指定的联系人、群名或 ID 查找会话。需要继续查找时沿返回的 `nextOffset` 分页；没有匹配就说明未找到。多个可能匹配的会话先请用户选择，再按选择继续。
2. 使用查询结果的 `id` 作为 `get_wechat_history` 的 `session_id`，默认读取最近 50 条消息。按 `isSelf` 识别用户消息，结合 `senderId` 区分其他发送者；群聊按成员分别理解。保留消息时间，按时间顺序理解对话。
3. 只有当前问题依赖更早信息时，才使用同一会话上一页返回的 `next` 作为 `before` 继续读取。找到回复所需信息后立即停止查询，即使 `next` 仍有值；只有关键信息仍缺失且 `next` 不为 null 时，才读取上一页。

MCP 不可用或查询报错时记录为读取错误，并说明未能取得历史；空结果记录为本次读取没有消息。若已有材料仍足够，按已有材料继续；否则请求补充关键聊天或信息。

非文本占位只说明消息类型，不包含图片、语音、视频或附件正文。若其实际内容影响回复，请用户补充。

## 3. 整理信息归属、来源与时间

每条相关信息保留“谁提供、何时提供、来自哪条聊天或用户说明”。按用户与对方分别整理，并标注自述或转述来源。

事实摘要记录明确提供的信息，保留实际语气和称呼。需要用户补充的经历、理由、承诺或立场才能写时，先补问当前缺少的关键内容；能写出不依赖缺失信息的回复时直接写。例如用户只说“不想去”，可以直接拒绝；用户要求说明真实原因时，先确认原因。

普通语气反应不需要先做事实调查。

按时间和适用情境整理旧记录。用户本次明确表达的意愿作为当前意愿；仍影响本轮回答的历史事实冲突单独整理并澄清。需要确认用户当前意愿时向用户补问；待回复消息与历史记录有冲突时，在回复中向对方确认。

能由时间顺序或明确更正解释的信息，按其适用时段整理。仍影响本轮回答的事实冲突先澄清；无关缺失或矛盾不阻塞回复。

## 4. 交给回复阶段

形成简短内部摘要，包含：

- 待回复消息与用户本轮目标；用户未说明的目标标记为未说明。
- 相关聊天逐条列出，保留原文、发送者、来源和时间；用户提供材料没有时间时标记未提供。
- 用户与对方分别已提供的补充信息，保留来源、时间和自述或转述性质。摘要里的聊天消息列入 relevant_messages；user_information 和 other_information 汇总相应补充信息。
- 会影响回复的缺失或矛盾，以及读取状态（未需查询、成功、空结果、错误或不可用）。

完成条件是已整理足够的可追溯材料供回复生成，或已明确指出需要用户补充的关键内容。摘要无需默认展示给用户；共享背景作为语境，不要求在回复里逐项复述。
